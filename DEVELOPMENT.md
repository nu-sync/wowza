# Development decisions

## 2026-11-06: Public repository preparation

The public destination is `nu-sync/wowza`, with MIT selected by the maintainer. README labels the Windows CLI experimental and keeps source setup and core flows brief. Cargo declares Rust 1.91, the license, and repository URL. GitHub Windows checks run the locked formatting/lint/test/build workflow, then produce an executable ZIP and SHA-256 checksums as temporary test-build artifacts. Publishing a player-facing prerelease remains a separate step described in `docs/PUBLISHING.md`.

Packaging uses default production behavior without interruption hooks, remaps local compiler paths, and includes project, dependency, and Rust standard-library notices. Model checks now run with Java/TLC alone; the optional statechart worker only regenerates diagrams. Both standalone and diagram routes passed all seven models and three expected counterexamples. The locked application check script passed 32 default and 37 interruption-enabled tests, formatting, Clippy, and release compilation.

The extracted Windows ZIP passed checksum verification, startup, saved configuration, read-only preview, two-folder install/update/removal, and preservation of saved settings in a temporary installation. Setting the interruption-test environment variable did not interrupt the production executable. The remapped executable contained no local username in ASCII or UTF-16 checks. This verifies the package on the development machine, not on a fresh player machine.

A publication privacy review found local profile paths in saved TLC output and personal author metadata in the unpublished initial commit. Saved logs now replace paths and machine details while preserving model outcomes. The public history uses a project identity, and the original unpublished commit is removed before upload. Build output and local settings are ignored. Gitleaks and checks for personal identifiers cover the final committed content and reachable history; no live game configuration is included. Fresh-machine and in-game player verification remain outstanding.

## 2026-11-06: Review fixes and delivery

The review reproduced two defects before changing their implementation. First, an `Interface` junction let installation writes reach a different temporary game installation, including when the junction was introduced after preview. Both `Interface` and `Interface/AddOns` are now checked as normal directories before preview and execution. Regression tests exercise both locations and timings, checking that the other installation remains untouched.

Second, recovery dry runs reported success with modified backup contents even though execution would refuse them. Recovery now uses the same read-only move planner for preview and execution; execution repeats the checks under the installation lock. Tests modify backups after an interrupted two-folder update, before and after preview, and require refusal with no file changes. Existing recovery interruption/retry cases still pass.

`scripts/check.ps1` passed formatting, all-target/all-feature Clippy, 32 default tests, 37 tests with interruption hooks, and a release build. `cargo test --release --test workflows` passed all six workflow tests. `scripts/check-models.ps1` passed all seven models; the two new models check 10 and eight distinct states. Disabling their guards reproduces `SameInstallation` and `HonestPreview` violations, matching the real failing-before regression tests. The existing stale-input negative control also fails as expected. Reports, shortest counterexample paths, assumptions, and reproduction commands are in `models/README.md`.

README now covers setup, status, search/install, update/remove, and recovery in a short usage guide; detailed options live in `docs/REFERENCE.md`. `AGENTS.md` describes contributor conventions. The folder had no Git metadata, so a repository was initialized with the configured default branch, `master`; build output is ignored. This review was a local self-review with real temporary Windows installations. In-game behavior, concurrent external changes during individual filesystem operations, and power-loss durability remain unverified.

## 2026-11-06: Simplification implementation contract

Implement the four selected improvements for players and contributors: a shared package inspection, prepared changes with read-only previews, reusable real-filesystem failure scenarios, and remembered installation/recovery context. Existing command names remain supported. Add status, configuration, JSON previews, and dry runs without changing ownership formats. Preserve no-overwrite moves, lock ownership, stale-preview rejection, saved settings, and explicit confirmation. Configuration precedence is explicit path, environment, saved path, then the existing default.

Baseline: version 0.1.0, Windows, 24 passing tests; no Git metadata or user telemetry. A temporary two-folder package appears twice in current list output. Local source, tests, documentation, and lifecycle models are authorized for change; publishing and live game mutations are outside scope. All write verification uses temporary installations. Check package grouping against files, stale previews against changed ZIPs/packages, interruption recovery against original bytes, and path isolation using two installations. Run formatting, all-target Clippy, default and failure-injection tests, and bounded TLC models. Keep statechart work outside the repository and retain reproducible model sources and reports. No external accounts are required; player usability observation remains unavailable.

## 2026-11-06: Simplification verification

The default status view groups consistent ownership records into packages and diagnoses missing, modified, or conflicting folders. List, scan, doctor, and JSON share one inspection, which reads each package's contents once per inspection. Prepared install/update/remove/recovery plans capture absolute installation/input paths and private preconditions; execution consumes the plan and rechecks those preconditions under the existing lock. Removal now rejects a changed package fingerprint as well as a changed folder list. Recovery binds confirmation to the journal fingerprint. Legacy ownership parsing and the folder-move algorithms remain intact.

Configuration tests exercise explicit/environment/saved precedence, replacing saved settings, invalid settings, and moved installations. Recovery selection covers none/one/multiple pending operations; a generated PowerShell recovery command was executed against a path containing spaces and an apostrophe while another installation was selected by the environment. Preview/cancellation tests compare complete directory and byte snapshots. Controlled browser tests exercise decline, success, and opening failure without launching a browser.

`scripts/check.ps1` passed formatting, all-target/all-feature Clippy, 30 default tests, 33 tests with interruption hooks, and the optimized release build. The three interruption tests include 14 install/update/remove boundary cases, six recovery interruption/retry cases, and journal/path/selection cases. They terminate child processes with no unwinding after journal publication, every folder move, and commit; byte snapshots, unrelated files, and WTF settings are checked. These simulate abrupt process termination, not power loss. The hooks exist only with the explicit `test-hooks` feature.

`scripts/check-models.ps1` passed all five bounded models: Lifecycle (11 states), Update (16), Handoff (7), Plan (21), and RecoveryChoice (41). The negative control deliberately removes input freshness enforcement and fails the unchanged invariant; Rust tests refuse the corresponding stale inputs. Generated reports and charts are in `models/reports/`. The Windows shell wrapper failed because it assumes `/bin/sh`; the checked-in runner uses the same skill's worker/checker/generator directly. TLC state output is isolated per model to avoid timestamp collisions. In-game behavior, external-manager concurrency, power-loss durability, non-Windows lifecycle operations, and observation by real players remain unverified.

## 2026-11-05: Package lifecycle work

The initial single-folder installer is not sufficient for add-ons distributed as multiple folders. The current work separates archive validation, package lifecycle, and CurseForge API research. The goal is to preserve existing add-ons, journal multi-folder operations before moving anything, refuse ambiguous ownership or conflicts, and provide explicit recovery. Tests use temporary installations; the player's live installation is not a test target. API-dependent search, downloads, and release selection must not assume undocumented endpoints or claim verified Forever compatibility without evidence.

The directory tree is shared: `src/manage.rs` and `src/archive.rs` have separate owners; CLI, integrated tests and documentation are integrated centrally. Completion requires exercising real CLI behavior, including interrupted operations and modified files, and documenting unresolved limits.

## CurseForge integration evidence

The [documented CurseForge API](https://docs.curseforge.com/rest-api/) provides search, version types, fingerprint matching, file metadata and download URLs, and requires an API key. [Third-party API access requires an application and approval](https://support.curseforge.com/support/solutions/articles/9000208346-about-the-curseforge-api-and-how-to-apply-for-a-key); [authors can restrict third-party distribution](https://support.curseforge.com/support/solutions/articles/9000207877-project-distribution-toggle). A [Leatrix Plus release page](https://www.curseforge.com/wow/addons/leatrix-plus/files/9447133) marks that file for Forever 1.60.1. This does not establish the live API's Forever version-type ID, response shape, or download availability. Those require an authenticated test; the website download endpoint is not treated as a supported third-party API. No credentials or undocumented API are required by Wowza's current workflow.
## 2026-11-05: Integration review

Independent review identified that checking for pending transactions alone does not serialize concurrent Wowza processes. The lifecycle implementation must hold an OS-released exclusive lock across pending checks, moves and recovery. Recovery records are external input and must use the same Windows component validation as ZIP entries. Integration tests also cover multi-folder conflicts, modified packages and recovery without overwrites. External add-on managers remain outside Wowza's lock.

## 2026-11-05: Integrated outcome

Package operations now journal and lock Wowza's own writers, preserve legacy ownership records, and recover interrupted moves to the prior state without replacing occupied destinations. Review found and fixed a recovery path traversal (folder component validation now rejects both separators), and imposed metadata size limits before moves. `cargo test` covers interrupted install/removal simulations, lock contention, traversal, multi-folder conflict and changed content; `cargo clippy --all-targets -- -D warnings` and `cargo fmt --check` passed. The actual Leatrix Plus ZIP was installed, byte-compared, listed as managed, and removed into a recovery directory in a temporary installation; `doctor` inspected the live installation read-only. Power-loss durability, concurrent non-Wowza managers, and a real in-game launch remain unverified. API-backed functionality and update/rollback remain open work pending verified behavior and data sources.

## 2026-11-05: Updates and lifecycle models

A keyless update command accepts a user-selected ZIP, verifies the existing package and archive fingerprint again after confirmation, requires the existing folder set, journals the replacement and retains the original. Recovery restores the original after an interrupted update. A stale confirmation could otherwise update a different package version with the same folder names; the command now compares the confirmed package fingerprint under the operation lock. TLC checked bounded lifecycle, two-folder update, and handoff models; see `models/README.md` for assumptions, diagrams, and reproducible commands. The tests include nine two-folder recovery arrangements, conflict and retry, stale confirmation and command cancellation. The real Leatrix archive was used on both sides of an isolated update; that checks bytes and backup but does not establish selection of a newer release. The live game installation was not modified.
